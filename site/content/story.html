Port against an oracle

Each OCaml module in upstream's haxe/src became a Haxe module at the same path, with its functions, branches and data in the same order. The reference compiler, built from the pinned commit, is the oracle: same arguments, same HXB, byte for byte. An earlier attempt that reimplemented parts by hand was dropped for this.

OCaml leaks into the output

Most early mismatches were OCaml behaviour: Hashtbl iteration order (reproduced bucket by bucket), sorted PMap iteration, right-to-left argument evaluation, physical equality, 63-bit integers, float printing. These are emulated in src/core/ds.

Macros

A port of the Eval interpreter and the macro API. Then the 66 macro cases, --interp, the compilation server, display and haxelib, each checked against the reference.

A back end of its own

On the existing targets the port ran 1.3× to several times slower than OCaml. hxc, a back end that wrote C, closed the gap: built with clang, it compiled itself with about 13% less CPU and 15% less memory than the OCaml compiler. hxmc started as hxc's second back end, writing x86-64 instead of C, and grew into a target: SSA, a register allocator, ARM64, WebAssembly, its own ELF, PE and Mach-O linkers, a runtime in Haxe. It builds itself, so hxc was removed; the releases, lix and the playground are all built by hxmc.

Upstream's tests

Upstream's target-independent CI job (unit, misc, threads, display, server, two third-party projects) passes on the native build, and found bugs the conformance cases missed.

Every target

The JS, Lua, Python, PHP, Neko, HashLink, JVM, C++ and SWF generators came last, with the OCaml libraries they use (Neko bytecode, SWF and ABC writers, zlib deflate). A fuzzer generates well-typed programs and compares each target's output with the reference's.

Keeping up

The pin moves forward one upstream commit at a time, ported and rerun through the full test matrix.
