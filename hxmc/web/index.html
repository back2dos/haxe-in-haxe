Haxe in Haxe

A port of the Haxe compiler from OCaml to Haxe. hxmc, a Haxe target that writes machine code and WebAssembly itself, compiles it to native binaries for Linux, macOS and Windows, and to WebAssembly for the playground below.

It takes the same arguments as haxe. Every build is made by hxmc on Linux (machine code, its own linker, no C compiler for the port's code) and carries mbedtls and libuv, so sys.ssl and eval.luv work in macros and --interp. hxmc

		
The port is built by hxmc, a Haxe target written for it: from the typed program it writes x86-64 and ARM64 machine code with its own register allocator and linkers (ELF, PE, Mach-O), or a WebAssembly module, with a precise generational collector and threads; no C compiler, assembler or system linker runs when a program is built, and every target is cross-built from Linux. hxmc builds itself. See hxmc/README.md.

	


	

		
Tools

		
lix (~2 MB): lix, the Haxe package manager, and haxeshim, ported from Haxe on Node.js and compiled by hxmc, one binary per platform. It is lix, haxe, haxelib and neko in one file: it acts as the command it is named or linked as.

		
    
			
  • Linux: x86-64, ARM64
    • 
			
  • macOS: x86-64, ARM64
    • 
			
  • Windows: x86-64, ARM64
    • 
		

		
Install it as lix in a directory on your PATH and let it create the haxe, haxelib and neko commands next to itself (lix shims). Linux (lix-linux-arm64 on ARM64):


curl -fLo ~/bin/lix https://haxe-in-haxe.ben.mk/tools/lix-linux-x86_64 && chmod +x ~/bin/lix
lix shims                       # symbolic links: ~/bin/haxe, ~/bin/haxelib, ~/bin/neko

		
macOS (lix-macos-x86_64 on Intel):


curl -fLo ~/bin/lix https://haxe-in-haxe.ben.mk/tools/lix-macos-arm64 && chmod +x ~/bin/lix
lix shims                       # symbolic links: ~/bin/haxe, ~/bin/haxelib, ~/bin/neko

		
Windows (PowerShell; lix-windows-arm64.exe on ARM64), e.g. into C:\tools, a directory on your PATH:


curl.exe -fLo C:\tools\lix.exe https://haxe-in-haxe.ben.mk/tools/lix-windows-x86_64.exe
lix shims                       # hard links: haxe.exe, haxelib.exe, neko.exe

		
Then, in a project: lix downloads Haxe versions and libraries into the project's scope, and haxe runs the version and libraries of the scope it is called in, so editors and build scripts that call haxe get the right ones:


lix scope create                # a .haxerc for this directory
lix install haxe 4.3.7          # download it and use it here
lix +lib tink_core              # haxe_libraries/tink_core.hxml
haxe -lib tink_core --run Main  # runs Haxe 4.3.7 with tink_core
lix use haxe 4.3.6              # switch to another downloaded version
lix download                    # after a clone: the scope's Haxe and missing libraries

		
The haxe shim adds about 2 ms to a compiler call (Node.js: about 60 ms). The compiler server modes (--wait, --server-listen, --server-connect) run on libuv with hxcoro coroutines. Compared with the npm package on 26 scenarios, output and installed files are identical. Details: tools/lix/README.md.

	


	

		
Status

		
The port follows upstream (haxe/src, commit 995a7d1) module by module. For the same arguments it should produce the same output as the reference compiler; this is tested for:

		
    
			
  • HXB output: 279 of 279 conformance cases (and the 7 the reference rejects), 66 of 66 macro cases;
    • 
			
  • every target (JS, Lua, Python, PHP, Neko, HashLink, HL/C, JVM, C++, SWF) and --xml/--json, with a differential fuzzer and upstream test projects;
    • 
			
  • --interp, display requests, the compilation server and the Eval debugger;
    • 
			
  • upstream's target-independent CI job (unit, misc, threads, tink_core, hxcoro), which passes with the native build.
    • 
		

		
Details: test/TESTING.md.
